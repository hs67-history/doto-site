# UbuntuでOpenClawを自動起動するまでの記録

ブログ「道東に暮らして」の制作にOpenClawを活用するため、Ubuntuでの自動起動設定から、ブログのファイル読み取り、記事作成までを進めました。途中でGatewayの二重起動にも遭遇しましたが、既存のプロセスを確認して停止し、サービスとして起動できました。

この記事は、実際に確認した作業記録をもとにまとめたものです。自動起動やトラブル対応などは作業者から提供された確認記録を、HTMLの読み取りとMarkdown作成はこの会話で確認できた結果を反映しています。掲載コマンドは作業当時の記録であり、記事の修正にあたって再実行したものではありません。

作業時の環境は次のとおりです。

- OS：Ubuntu 26.04.1 LTS
- OpenClaw：2026.10.9
- GitHub CLI：2.46.0

## 1. OpenClawを導入した目的

OpenClawを活用する目的は、ブログ「道東に暮らして」の制作を手伝ってもらうことです。このブログでは、北海道・十勝の大樹町を拠点に、歴史や自然、人の営みを記録します。

既存のページを読み取って構成を説明してもらい、作業記録や地域の記録を記事にまとめることを目指しました。毎回手動でGatewayを起動する手間を減らすため、自動起動の設定も行いました。

Linuxの操作では、コマンドの目的を一つずつ確認することを大切にしています。ファイルを読むだけの操作と、ファイルやシステムの設定を変更する操作を分け、変更する対象を明確にして進めました。

## 2. systemdによる自動起動設定

systemdは、Ubuntuでバックグラウンドのプログラムなどを管理する仕組みです。管理するプログラムの単位を「サービス」と呼びます。今回はOpenClawのGatewayを、ユーザー単位で管理するsystemdユーザーサービスとして登録しました。

**手順1：Gatewayのサービスを登録する**

```bash
openclaw gateway install
```

この操作で、systemdユーザーサービスとして登録しました。以降の確認に使ったサービス名は `openclaw-gateway.service` です。

**手順2：自動起動が有効かを確認する**

```bash
systemctl --user is-enabled openclaw-gateway.service
```

結果は `enabled` でした。これはサービスの自動起動が有効になっていることを示します。`--user` は、システム全体ではなく、そのユーザーのサービスを操作する指定です。

**手順3：現在の動作状態を確認する**

```bash
systemctl --user status openclaw-gateway.service --no-pager
```

結果は `active (running)` でした。サービスが現在動作していることを示します。`--no-pager` は、結果をページ送り用の画面に切り替えず表示する指定です。

`enabled` と `active (running)` は意味が違います。前者は自動起動の設定、後者は現在の動作状態を表します。

**手順4：PCの再起動後にも確認する**

PCを再起動した後、次のコマンドで確認しました。

```bash
systemctl --user is-active openclaw-gateway.service
```

結果は `active` でした。再起動後の確認時にも、Gatewayが動作していることを確認できました。

なお、ユーザーサービスの起動条件と、ログイン前からの動作は別の話です。この記録では、ログイン前の段階で動いていたかまでは扱わず、「PC再起動後の確認でactiveだった」という確認結果を記載しています。

## 3. Gatewayの二重起動トラブルと解決

Gatewayは、OpenClawの接続ややり取りを支えるプログラムです。設定作業の途中で、Gatewayの起動が終了コード `78` で失敗するトラブルがありました。

終了コードは、プログラムがどのように処理を終えたかを表す番号です。ただし、この番号だけで原因を決めつけず、ログを確認しました。

**手順1：ログから既存Gatewayを確認する**

`journalctl` でログを確認したところ、PID `96988` の既存Gatewayが、同じ状態ディレクトリを使っていることが分かりました。状態ディレクトリとは、プログラムが動作に必要な状態を保存する場所です。PIDは、実行中のプログラムを識別する番号です。

ログ確認に使った `journalctl` の詳しいオプションや、ログ全文は記録に含まれていないため、ここでは補っていません。

**手順2：通常の停止操作を行う**

```bash
openclaw gateway stop
```

この操作では既存のPIDが残りました。そこで、確認済みのプロセスに終了を要求しました。

```bash
kill -TERM 96988
```

`-TERM` は、対象のプロセスに終了を要求する指定です。この操作で既存Gatewayを停止しました。

**96988はこの作業時のPIDです。別の機会にそのまま使う番号ではありません。** PIDは変わるため、同様の対応では対象を確認する必要があります。

**手順3：ポートが解放されたことを確認する**

```bash
ss -ltnp '( sport = :18789 )'
```

ポートは、通信を受け付ける窓口の番号です。このコマンドでTCPポート `18789` の待ち受け状態を調べ、ポートが解放されたことを確認しました。

**手順4：systemdからGatewayを起動する**

```bash
systemctl --user start openclaw-gateway.service
```

この操作で起動に成功しました。今回のトラブルは、既存Gatewayが残っていたことをログで確認し、それを停止してからサービスを起動することで解決しました。

## 4. GitHub CLIのインストールと認証

GitHub CLIは、GitHubをコマンドで操作するための道具です。コマンド名は `gh` です。

**手順1：GitHub CLIをインストールする**

```bash
sudo apt install gh
```

この操作でGitHub CLI `2.46.0` を導入しました。`apt install` はUbuntuでソフトをインストールする操作、`sudo` は管理者権限で実行するための指定です。

**手順2：GitHubのアカウントで認証する**

```bash
gh auth login
```

案内に沿って、次の選択をしました。

1. 接続先は `GitHub.com`。
2. 接続方式は `HTTPS`。
3. 認証方法はブラウザ認証。

結果として、GitHubアカウント `hs67-history` での認証に成功しました。認証とは、利用するアカウントを確認して、操作を許可する手続きです。

## 5. ブログ用リポジトリのコピー

リポジトリは、ファイルとその変更履歴を管理する保管場所です。GitHub上のリポジトリを手元に複製することを「クローン」と呼びます。

**手順1：ブログ用リポジトリをクローンする**

対象は `hs67-history/doto-site` です。

```bash
gh repo clone hs67-history/doto-site ~/doto-site
```

このコマンドでクローンに成功しました。`~` は、そのユーザーのホームフォルダを表します。今回の保存先は `/home/hs67/doto-site` です。

**手順2：記事を置くフォルダを作る**

```bash
mkdir -p ~/doto-site/articles
```

記事用の `articles` フォルダを作成しました。`mkdir` はフォルダを作るコマンドで、`-p` は必要な親フォルダも作成し、対象のフォルダがすでにあってもエラーにしない指定です。

ブログのトップページは `/home/hs67/doto-site/index.html`、今回の記事の保存先は `/home/hs67/doto-site/articles/openclaw-setup.md` です。

クローンはGitHubから手元へコピーする操作です。手元で記事を書くだけでは、その記事が自動的にGitHubへ送られるわけではありません。

## 6. OpenClawのファイル読み取り設定

初期設定では、OpenClawの `tools.profile` は `minimal` でした。これは、OpenClawに使わせるツールの構成に関する設定です。

最初の読み取り依頼では、アシスタントから「この会話で利用できるツールに、PC内のファイルを読み取る機能がない」という回答がありました。そこで、設定をバックアップした後、プロファイルを変更しました。

```bash
openclaw config set tools.profile coding
```

変更後には、Gatewayの再起動は不要というメッセージが表示されました。その後、`index.html` の読み取りに成功しました。設定バックアップの具体的なコマンドや保存先は提供された記録にないため、ここでは記載していません。

読み取りテストでは、ファイルの場所を省略しない「絶対パス」を使いました。実際に実行されたコマンドは次のとおりです。

```bash
cat /home/hs67/doto-site/index.html
```

`cat` は、ファイルの内容を表示するコマンドです。この操作自体はファイルを書き換えません。結果としてHTMLの内容が表示され、終了コードは正常終了を示す `0` でした。

読み取りによって、次の内容を確認できました。

- HTMLのタイトルは「道東に暮らして」。
- 上部の説明文は「北海道・大樹町の歴史と自然を記録するブログ」。
- ナビゲーションは、歴史・地名・考古学・植物・鳥・昆虫・石碑・お店・産業の9項目。
- 各項目は、同じページ内の対応する場所へ移動する構成。
- デザイン指定は、生成り色の背景、濃い青灰色の上部と最下部、白い角丸の枠。

これはHTMLの内容とデザイン指定の確認であり、ブラウザ上での表示確認とは区別しています。また、ツールの設定変更は、あらゆるファイルの操作や公開を無条件に任せるという意味ではありません。実際の作業では、対象ファイルと変更の範囲をその都度指定します。

## 7. 今後のブログ制作への活用

ファイルの読み取りに続いて、OpenClawによるMarkdownファイルの作成にも成功しました。Markdownは、見出しや箇条書きを簡単な記号で書ける文章の形式です。今回の記事も、その形式で保存しています。

これからは、地域の歴史や自然の観察記録を記事にまとめる作業に活用していきます。たとえば、次のような使い方が考えられます。

- 観察メモを整理して、記事の見出しを作る。
- Linuxの作業記録を、初心者にも読みやすい文章にまとめる。
- 既存の記事を読み取り、表現や構成を見直す。
- 確認済みの事実と、これから調べることを分けて整理する。

地域の歴史、地名の由来、動植物の名前は、資料や現地の記録と照らし合わせて確認します。AIの文章をそのまま事実とせず、今回のように実際の記録をもとに修正していくことを大切にします。

今回、Gatewayのサービス登録と再起動後の動作確認、二重起動の解消、GitHub認証、リポジトリのクローン、HTMLの読み取り、Markdown記事の作成まで進めることができました。

なお、今回の記事修正は `articles/openclaw-setup.md` だけを対象にしています。既存の `index.html` やシステム設定は変更せず、commitやpushも行っていません。commitは変更をGitの履歴に記録する操作、pushはその履歴をGitHubなどへ送る操作です。記事の保存と公開を分け、内容を確認しながら制作を進めていきます。
